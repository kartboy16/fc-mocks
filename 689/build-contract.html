#689 Advisor brand colours on calculators: build contract

Issue: #689. Mocks: hub. Not agent-ready. Soft Dev hold until Alex picks.

Today (read-only, at 6499dd7)

  • Colour setting: the only colour advisors can set is primaryColour (default #1976d2). Its picker sits in the advisor setup Customize & Deploy step (imports/ui/AdvisorConfigManager.jsx, under the custom CSS box).
  • It's used for the article-list embed buttons (server/api/embed.js) and the Website hub. It isn't used for calculators.
  • Company Branding step: logo, Company Name, Tagline, Disclaimer. No colour.
  • Admin "Edit advisor" (imports/ui/AdminUserEdit.jsx): profile fields, profile photo and company logo. No colour, and no record of who changed what.
  • Calculators: all 53 live calculators use the same two colours, main #1F4E5F and accent #4A90A4. Charts use them too. These live in the post content, not in the repo.
  • Serving: server/api/html-post-serve.js serves /html-post/:id.
  • It wraps the HTML and adds a resize script.
  • It records a view when ?advisorId= is present.
  • It sends Cache-Control: no-store.
  • It doesn't read the advisor's settings.
  • Surfaces: every one already passes advisorId: WordPress embeds, the embed API, the FC post page, email links and the compliance PDF link (server/website-compliance-pdf.js).
  • Report name and logo: these come from ?advisor= and ?logo= (imports/utils/htmlPostFrameSrc.js, which uses safeCalculatorDisplayName so emails are never shown). Only new links have them (PR #412), so older embeds print "your advisor" with no logo.

Recommendation: A, a Brand colours card inside Company Branding

  • A adds a Brand colours card under the logo in Company Branding:
  • On/off switch, main colour, and an optional accent.
  • Plain-words contrast messages.
  • A live before/after preview of a calculator and its chart.

The old picker in Customize & Deploy becomes a pointer ("Brand colour has moved… Edit in Company Branding"). Colour sits next to the logo, which is where advisors look for it, and the issue asks for it there. It's the smallest UI change. - B: a separate Calculator look section with a gallery of 4 calculators, plus a "Your colours / Standard teal" switch. Company Branding links to it. - Pros: a richer preview. - Cons: colour lives away from the logo, even though the same colour also drives the article list. It's one more place to find. - C: same as A, plus colours suggested from the logo (swatches, with click for main and shift-click for accent) and a manual override. - Pros: friendly, and gives good first picks. - Cons: extraction is unreliable for single-colour, tiny or transparent logos, and it's about 1.5–2 extra days. - It could be added to A later.

Build note

  1. Storage on advisor_configs:
  2. Keep primaryColour as the main colour. It's the existing field and still drives the article list, so there's no duplicate.
  3. Add calculatorColoursEnabled: Boolean (default false) and accentColour: String|null.
  4. Add audit fields: brandColoursUpdatedAt, brandColoursUpdatedBy (userId), and brandColoursUpdatedVia ('company-branding'|'admin'|'migration').
  5. Add the new fields to the Match schemas (lines 264 and 357), toPublicAdvisorConfig if the client needs them, and the AdminUserEdit save method.
  6. Validation:
  7. Accept only #rgb or #rrggbb, normalised to lowercase #rrggbb. Reject anything else on the server.
  8. Treat #1976d2 (any case) as not set.
  9. Because only that pattern can reach the page, injection is safe.
  10. Contrast (WCAG 2.x relative luminance):
  11. The main colour must be at least 4.5:1 against white (white text on headers and buttons).
  12. The accent must be at least 3:1 against white (chart bars and highlights, which are non-text, on a white page).
  13. Auto-darken:
  14. Convert to HSL and lower lightness by 5 points per step, for up to 6 steps (30 points). Keep hue and saturation. The first step that passes wins.
  15. If none pass, fall back: main to #1F4E5F, accent to #4A90A4.
  16. With no accent set, use the main colour mixed 35% with white, darkened to 3:1, otherwise the main colour itself.
  17. Results: #f4c430 becomes #846507 after 6 steps, and #fdf3dc falls back to teal.
  18. Use one shared util (imports/utils/brandColours.js) on the client (messages and preview) and the server (injection), with unit tests covering the cases above.
  19. Injection (html-post-serve.js):
  20. When advisorId is present, load the advisor's config. If it's enabled and resolves, inject at the top of <head>, before any calculator script, <style id="advisor-brand">:root{--…main:#..;--…accent:#..}</style> plus <script>window.__ADVISOR_BRAND={main:'#..',accent:'#..'}</script>.
  21. To confirm in the post content: how the 53 calculators read their two colours (CSS variables, or JS constants for Chart.js).
    • If they're hard-coded hex values, the fallback is a server-side, case-insensitive replace of #1F4E5F and #4A90A4 in the served HTML only. The stored post is never edited.
  22. Off, missing, invalid or default blue: serve the HTML exactly as today, byte for byte apart from the resize script. Add a test for that.
  23. Report name and logo:
  24. When advisorId is present but ?advisor= or ?logo= is missing, the server fills them from the config: the name through safeCalculatorDisplayName (never an email), and the logo from companyLogoUpload as an absolute URL.
  25. Do this by injecting window.__ADVISOR_REPORT={name,logo} and having the calculators' existing query reader fall back to it, or by rewriting location.search before the scripts run. Pick whichever the calculators' code allows.
  26. Values from the URL still win.
  27. What picks it up: all 53 calculators and their charts, on every surface that goes through /html-post/:id?advisorId=: WordPress embeds, the embed API, the FC post page, email links and the compliance PDF link. The printed or PDF report uses the page's colours, because it's printed from the same page.
  28. Caching:
  29. /html-post stays no-store.
  30. Cache the colour and name lookup per advisorId in memory for about 60 seconds, and clear that entry on save. A change shows on the next load.
  31. WordPress page caches only hold the iframe tag, not the calculator HTML, so they aren't affected.
  32. Migration:
  33. Nothing to copy: existing primaryColour values become the main colour.
  34. Values equal to #1976d2 count as unset.
  35. Set calculatorColoursEnabled: false for everyone, so no live calculator changes until the advisor or staff turns it on (open question).
  36. Write brandColoursUpdatedVia: 'migration' for anyone who has a non-default colour.
  37. Customize & Deploy: remove the <input type="color"> and show the pointer box with the current swatch and a link to the Company Branding step.

Open questions

  1. Default for existing advisors: should brand colours be off until turned on (as mocked), or on for anyone who already chose a non-default primaryColour?
  2. Should the article list keep using the main colour, or should it get its own setting later?
  3. Are 4.5:1 for the main colour and 3:1 for the accent the right bar? Should we allow a dark main colour with dark text instead of white?
  4. Is the darkening limit right (up to 30 points of lightness), or should we fall back sooner so colours stay recognisable?
  5. How do the 53 calculators read their colours (CSS variables or JS)? Is the hex-replace fallback acceptable?
  6. Should advisors see "Updated by FC support" when staff change their colours, or the staff member's name?
  7. Should the report logo use companyLogoUpload or a separate report logo? What should it do with very wide or very tall logos?
